# 사용자 파일럿 진행 스크립트 (카드 E3)

> **2026-10-12: 이번 논문에서는 파일럿을 생략하기로 했다(리스크 R7).** 이 문서는 나중에 파일럿을 할 때를 위해 남겨 둔다.

목적: 사람 6~10명이 데모 화면에서 승객과 기사를 번갈아 맡아 거래를 **30건 이상 체결**한다. 이를 통해 "사람 승객이 가장 싼 호가를 고르는가"를 예비로 관찰한다(ml-design v5 §8.2. 시뮬레이션만으로는 주장하지 않는 내용).

**기록하지 않는 것:** 참가자 이름·연락처·사진은 어디에도 적지 않는다. 화면 캡처, 메모, 출석표도 만들지 않는다. 서버에는 무작위 ID와 거래 기록(가격·시간·거리)만 남는다.

---

## 0. 준비 (진행자, 시작 30분 전)

1. 진행자 PC와 참가자 노트북·휴대폰이 **같은 와이파이**에 연결돼 있는지 확인한다.
2. 저장소 루트에서 서버 3개를 띄운다(터미널 3개).
   ```
   docker compose up -d redis
   cd PartB; python -m uvicorn app:app --port 8000
   cd PartA; ./gradlew bootRun --args="--deal.experiment-tag=pilot --admin.export-enabled=true"
   ```
   - Windows 방화벽 창이 뜨면 **개인 네트워크 허용**을 누른다.
   - 리허설은 `--deal.experiment-tag=rehearsal`로 띄운다. 거래 기록 DB(`PartA/data/`)는 서버를 껐다 켜도 남으므로, 리허설 거래가 `pilot`에 섞이지 않게 하려는 것이다.
3. 진행자 PC의 IP를 확인한다: PowerShell에서 `ipconfig` → "IPv4 주소"(예: 192.168.0.12). 참가자 접속 주소는 `http://<IP>:8080`이다.
4. 진행자 노트북으로 그 주소에 접속해 거래를 하나 만든다. **Price source가 QUOTE**인지 확인하고 취소한다. 이 확인 거래도 `pilot` 기록에 1건으로 남으며, 요약의 n_deals에 들어간다(CANCELLED라 체결 통계에는 영향 없음).
5. 아래를 준비한다.
   - **ID 쪽지**: 승객용 `R101`~`R110`, 기사용 `DR101`~`DR110`. 한 사람이 같은 번호의 R·DR을 한 장씩 뽑는다(예: R104와 DR104). 누가 몇 번을 뽑았는지는 적지 않는다.
   - **승객 상황 카드 3종**(여러 장): "급함 — 5분 안에 타야 함" / "여유 — 가장 싸게" / "보통"
   - **기사 제비**: "최소 희망 가격 = 기준가 × 0.80 / 0.85 / 0.90 / 0.95 / 1.00" 다섯 종류

## 1. 안내 (5분)

**구두 동의 문구 (그대로 읽는다):**

> "연구용 데모입니다. 이름·연락처는 수집하지 않고 거래 기록(가격·시간)만 남기며, 언제든 그만둘 수 있습니다."

이어서 설명한다.
- 승객은 출발지·도착지를 고르고 **Create deal**을 누른다. 기사들이 가격을 부르면 목록에서 마음에 드는 호가를 **Accept**한다. 원하는 가격을 **Send offer**로 제안할 수도 있다.
- 기사는 지도에서 내 위치를 클릭하고 **Go online**을 누른다. 목록에서 거래를 골라 가격을 부른다(**Bid**). 가격은 내릴 수만 있다. 승객 오퍼가 마음에 들면 **Accept offer**를 누른다.
- 거래는 **3분** 안에 체결되지 않으면 사라진다.
- "정답은 없습니다. 실제로 택시를 부르는 것처럼 하시면 됩니다." (정렬 기준이나 최저가를 고르라는 말은 하지 않는다.)

## 2. 라운드 (5분 × 6회)

**인원 나누기:** 라운드마다 **승객 1명당 기사 2~4명**이 되게 나눈다.

| 참가자 수 | 승객 | 기사 |
|---|---|---|
| 6명 | 2 | 4 |
| 7~8명 | 2 | 5~6 |
| 9~10명 | 3 | 6~7 |

라운드가 바뀔 때마다 역할을 교대해서, 모두가 승객과 기사를 각각 2번 이상 맡게 한다.

**각 라운드 시작 때:**
1. 승객은 **상황 카드**를 무작위로 한 장 뽑아 혼자 본다. 카드대로 행동한다.
2. 기사는 **제비**를 한 장 뽑는다. 승객의 거래 카드에 나온 기준가에 제비 숫자를 곱한 값보다 싸게는 운행하지 않는다.
3. **ID 입력:**
   - 승객: 자기 R 번호 그대로(예: `R104`). 매 라운드 같은 ID를 써도 된다.
   - 기사: **라운드마다 새 ID**를 쓴다. `DR104-r1`, `DR104-r2`, … (r 뒤는 라운드 번호)
     - 이유: 체결된 기사 ID는 거래 생성 후 **300초 동안** 다시 호가할 수 없다(운행 완료 가정, 명세 R10).
4. 기사는 지도에서 **서로 다른 곳**을 클릭해 위치를 잡는다. 승객 출발지에서 가까운 사람, 먼 사람이 섞이도록 진행자가 대략 정해 준다.

**라운드 진행 (5분):**
- 승객은 거래가 끝나면(체결·만료·취소) **곧바로 새 거래**를 만든다. 출발·도착 프리셋은 매번 바꿔도 된다.
- 목표 체결 수: 6라운드 × 승객 2~3명 × 라운드당 2~3건 ≈ 30~50건.
- 진행자는 라운드마다 체결 건수만 센다(참가자 정보는 적지 않는다).

**라운드 사이 (1분):** 상황 카드와 제비를 회수하고 역할을 바꾼다.

## 3. 정리 (5분)

1. 참가자에게 감사 인사를 한다. 끝.
2. **진행자 PC에서** 거래 기록을 받는다(저장소 루트):
   ```
   curl -o results/pilot/pilot_deals.csv "http://localhost:8080/api/admin/deal-history.csv?tag=pilot"
   python scripts/pilot/summarize_pilot.py
   ```
   → `results/pilot/pilot_summary.csv`가 만들어진다.
3. **n_matched ≥ 30**인지 확인한다. 미달이면 그대로 보고하고, 논문에 n을 적는다.
4. 서버를 끈다(Part A·Part B는 `Ctrl+C`, Redis는 `docker compose down`). 다음에 띄울 때 `--admin.export-enabled=true`를 빼면 내보내기 주소가 사라진다(404).

## 4. 요약 지표 (`results/pilot/pilot_summary.csv`)

정의는 `scripts/pilot/summarize_pilot.py` 맨 위 설명에 있다.

| 열 | 뜻 |
|---|---|
| n_deals / n_matched | 전체 거래 수 / 체결 수 |
| rider_picked_bid_share / driver_took_offer_share | 체결 중 승객이 호가를 골라 체결한 비율 / 기사가 승객 오퍼를 받아 체결한 비율 |
| n_rider_picked | 승객이 호가를 고른 체결 수. 아래 4개 지표의 분모 |
| rank1_share | 그중 그 시점 최저가 호가를 고른 비율 |
| n_rank_gt1 | 최저가가 아닌 호가를 고른 건수 |
| mean_extra_paid_ratio | (체결가 − 최저 호가) / 기준가의 평균. 최저가 대신 더 낸 돈의 크기 |
| mean_eta_saved_min | (최저가 기사의 픽업 ETA − 고른 기사의 픽업 ETA)의 평균. 더 내고 줄인 대기 시간 |

**논문에 쓸 때:** "예비 관찰(n = …)"로만 쓴다. 참가자 수가 적고, 상황 카드로 행동을 유도한 실험이라 일반화하지 않는다.
